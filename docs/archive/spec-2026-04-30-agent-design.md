# 竞品与需求分析 Agent — 设计文档

> 日期：2026-04-30
> 状态：已确认
> PRD 版本：v0.2

---

## 一句话定义

对话式亚马逊品类分析 Agent，用户自由提问，Agent 内部调度 4 个分析模块 + Sorftime 数据，输出分析结论和 PDF 报告。

---

## 架构

### 方案：路由 Agent + Skill 模块

Agent 分两层：

- **用户感知层**：理解意图、用用户语言沟通计划/进度/结果、生成报告
- **内部调度层**：意图→选择分析方法→加载对应 skill→调用 Sorftime→组织分析逻辑

用户不接触 skill 名、工具名、内部概念。Agent 用"做什么、要多久、得到什么"的方式沟通。

### 文件结构

```
agents/
└── 竞品与需求分析/
    ├── SOUL.md                # 轻量核心（~100行）
    ├── skills/                # 内部分析模块（用户不可见）
    │   ├── 市场调研.md
    │   ├── 竞品分析.md
    │   ├── 用户模型.md
    │   └── 交易模型.md
    ├── tools/
    │   ├── sorftime.md         # 数据工具调用指南
    │   └── report.md           # 报告生成规范+模板
    └── examples/
        └── 开场示例.md         # Agent 开场话术
```

## SOUL.md 设计

### 原则：轻量核心 + 渐进式加载

SOUL.md 控制在 ~100 行，只包含：
1. 角色定义（5行）
2. 对话原则（10行）
3. 意图识别 + 路由表（20行）
4. 对话流程规范（20行）
5. 质检标准（30行）
6. 报告生成触发（10行）

Skill 文件按需加载，不预加载全部。对话全程最大上下文控制在 ~500-600 行。

### 意图识别路由表

| 用户输入类型 | 分析方向 | 加载模块 |
|---|---|---|
| 关键词/品类 | 市场规模与机会 | 市场调研 |
| ASIN/链接 | 竞品对比分析 | 竞品分析 |
| 用户行为/评价 | 需求解构 | 用户模型 |
| 定价/转化问题 | 交易优化 | 交易模型 |
| 模糊方向 | 先提问澄清 | 视情况定 |
| 追问/深入 | 基于上下文继续 | 可能组合多个 |

### 渐进式加载

| 对话阶段 | 加载内容 | 上下文大小 |
|---|---|---|
| 空闲/开场 | SOUL.md（核心） | ~100 行 |
| 用户确认分析方向 | + 对应 skill 文件 | +200-300 行 |
| 执行数据采集 | + Sorftime 数据 | 按需 |
| 分析完成，质检 | + 质检清单 | 内置于 SOUL.md |
| 生成报告 | + 报告模板 | +100 行 |

## Skill 模块设计

### 从现有 skill 的变化

现有 skill（Claude Code 用的完整版本）→ Web Agent skill（精简版）：
- **去掉**：角色描述（SOUL.md 统一管理）、认知框架（避免重复加载）、PDF 生成逻辑（抽到公共模块）、归档逻辑（抽到公共模块）
- **保留**：执行步骤（核心）、对话输出规范（简化版）、报告章节模板（简化版）

### 每个 Skill 文件结构（约 150-200 行）

```
skills/市场调研.md
├── 适用场景描述（3行）
├── 执行步骤（主体）
│   每步：调用什么工具 → 获取什么数据 → 如何呈现给用户
├── 对话输出规范（10行）
│   中间结果怎么在聊天中展示
│   每步完成后给用户简短进度提示
└── 报告章节模板（20行）
    生成 PDF 时这部分内容如何组织
```

### 4 个 Skill 的分工

| Skill | 触发场景 | 主要数据源 | 核心输出 |
|---|---|---|---|
| 市场调研 | 用户给关键词/品类 | Sorftime 关键词+类目 | 市场规模、趋势、价格带、机会点 |
| 竞品分析 | 用户给 ASIN/链接 | Sorftime 产品+评论+特征 | 竞品对比、用户画像、痛点、机会 |
| 用户模型 | 讨论用户行为/需求/场景 | 评论数据 + 分析推理 | 需求结构、效用层级、切入点 |
| 交易模型 | 讨论定价/转化/成本 | 价格数据 + 分析推理 | 交易成本诊断、定价策略、转化建议 |

对话中可按需组合多个 skill，不限于单个。比如市场调研后追问用户画像，会追加加载用户模型。

## 对话流程

```
用户输入
    │
    ▼
① Agent 理解意图（加载 SOUL.md 核心）
    │
    ▼
② 告知用户计划（做什么、要多久、得到什么）
    │
    ▼
③ 用户确认 / 补充
    │
    ▼
④ 加载对应 skill，调用 Sorftime 数据，逐步展示
    │
    ▼
⑤ 质检（自检清单）
    │
    ▼
⑥ 总结核心结论
    │
    ▼
⑦ 用户选择：继续深入 / 生成 PDF 报告 / 结束
```

## 质检环节

分析完成后，Agent 内部执行自检：

### 质检清单

- **结论有数据支撑吗？** 每个核心结论至少有一个数据/评论/配置依据；没有数据的标注"待验证"
- **有模糊结论吗？** 不允许"可能""也许""大概"；不确定就用"数据不足，无法判断"或"待验证"
- **分析目标达成了吗？** 回头看用户最初的问题/需求，每个问题是否有明确回答
- **数据完整吗？** 应采集的数据是否都采到了；工具调用失败是否已标注；样本量是否足够支撑结论
- **建议可执行吗？** "价格建议 $25-35" 是；"可以考虑差异化" 否（太模糊）

### 处理方式

质检不通过 → 自动补全/修正 → 重新质检
质检通过 → 呈现给用户

### V2 预留

设计上预留子 Agent 审核接口。当自检质量不够时，可接入独立 reviewer agent（只需读分析结果 + 跑质检清单，不需要数据工具）。

## 数据层

### Sorftime 数据使用

两种使用场景：
- **Skill 内固定步骤**：按 skill 定义的流程依次调用
- **用户临时提问**：Agent 自行判断需要哪些数据，灵活调用

工具调用规范记录在 `tools/sorftime.md`。

---

## 报告生成

### 流程

1. 汇总本轮对话中的所有分析结果
2. 按报告模板组织内容（继承现有 skill 的报告结构）
3. 生成带样式的 HTML（A4 适配、中文字体、表格样式）
4. Chrome headless 转 PDF
5. 提供下载链接

### 公共报告模块

`tools/report.md` 包含：
- HTML 模板样式
- PDF 转换命令
- 各 skill 的报告章节结构

各 skill 文件只提供章节内容模板，不重复写样式和转换逻辑。

## 技术栈

### 后端：Python + FastAPI

- **Python**：与 Sorftime MCP 生态兼容性好，LLM 调用库成熟
- **FastAPI**：轻量异步框架，原生支持 SSE（流式响应）、自动 API 文档
- OpenAI 兼容协议，方便切换模型

### 模型：MiniMax M2.7

| 属性 | 值 |
|---|---|
| 架构 | MoE 230B/10B（总参 230B，活跃 10B） |
| 上下文 | 200K tokens |
| 价格 | 输入 $0.30/M tokens，输出 $1.20/M tokens |
| Tool Calling | 原生支持（function calling） |
| 协议 | OpenAI 兼容，可直接用 openai SDK 调用 |

选型理由：
- 成本低（约为同级别模型的 1/10），适合小团队免费试用
- 200K 上下文足够承载 SOUL.md + skill + 对话历史 + 数据
- 原生 tool calling 支持 Sorftime 工具调度
- OpenAI 兼容协议，后续可无缝切换其他模型

## API 封装方案

### 方案：自建后端 + 直接 LLM API

```
浏览器
  │ SSE（流式）
  ▼
┌──────────────────────────┐
│  后端（Python + FastAPI） │
│                          │
│  聊天 API                │
│  ├─ 接收消息             │
│  ├─ 读取 SOUL.md         │
│  ├─ 意图→加载 skill 文件  │
│  ├─ 拼接完整 prompt       │
│  ├─ 调 LLM API（stream）  │
│  │   ├─ 返回文本 → 流式转发
│  │   └─ 返回 tool_call → 执行后继续
│  └─ 工具执行层            │
│      ├─ Sorftime MCP     │
│      └─ PDF 生成          │
└──────────────────────────┘
```

### 核心模块

| 模块 | 职责 |
|---|---|
| Chat API | 接收消息，管理会话状态，SSE 流式响应 |
| Prompt Builder | 读取 SOUL.md，按意图加载 skill，拼接完整 prompt |
| LLM Client | 调用 MiniMax API，处理 stream 和 tool_call |
| Tool Executor | 执行 Sorftime MCP 调用、PDF 生成等工具 |
| Session Manager | 会话隔离，对话历史管理 |

### 多用户并发控制

- 3-5 人共享"个人级" API，通过后端集中管理
- API Key 后端统一持有，用户不直接接触
- 请求排队机制：同时请求时按队列处理，避免 API 限流
- 会话隔离：每个用户独立的对话上下文，互不干扰
- 用量监控：记录每次调用的 token 消耗，便于成本控制

### Sorftime MCP 桥接

Sorftime 是本地 MCP 服务，Web 环境下的调用路径：

```
LLM 返回 tool_call（工具名 + 参数）
    │
    ▼
后端 Tool Executor 识别工具名
    │
    ▼
通过 MCP 客户端调用 Sorftime 本地服务
    │
    ▼
返回数据 → 拼接为 tool_result → 继续对话
```

后端维护一个 MCP 客户端连接池，将 LLM 的 tool_call 请求转发到 Sorftime 本地服务。

## 设计决策汇总

| 决策项 | 结论 |
|---|---|
| 架构方案 | 路由 Agent + Skill 模块 |
| 后端技术栈 | Python + FastAPI |
| LLM 模型 | MiniMax M2.7（MoE 230B，200K 上下文，原生 tool calling） |
| API 封装 | 自建后端 + 直接 LLM API，不依赖第三方 Agent 框架 |
| 交互方式 | 对话式，隐藏内部概念 |
| 入口方式 | 全支持（关键词/ASIN/问题/方向） |
| Skill 选择 | Agent 判断意图→告知计划→用户确认→执行 |
| V1 Skill 数量 | 4 个：市场调研、竞品分析、用户模型、交易模型 |
| 输出形式 | 对话中展示过程 + 可生成 PDF 报告下载 |
| 报告生成 | HTML → PDF（Chrome headless），保持现有方式 |
| SOUL.md 策略 | 轻量核心（~100行）+ 渐进式加载 skill |
| 质检方式 | V1 自检清单（预留子 Agent 审核接口） |
| 多用户策略 | API Key 后端集中管理，请求排队，会话隔离 |
